# prd-draft — PRD 작성 Skill (요구사항정의서)

## 본질

PRD = **요구사항 정의서** (Product Requirements Document). 4 에이전트(서비스기획자·기술검토자·UX기획자·퍼블리셔)의 공통 SSOT 기준. *비전 문서*가 아닌 *요구사항 1건당 상세 명세 (BN시스템 16 필드 양식)*.

## 언제 쓰나

- 서비스기획자가 `/kickoff` [4] 병렬 진행 단계에서 자기 영역 PRD를 작성할 때 (4명 동시 spawn 시작점부터)
- **선행 조건**: `projects/<slug>/STATE.md` 존재 + `projects/<slug>/_broadcast.log` 생성됨

## §4-0 Mesh 5요소 정합 (M15)

본 Skill은 §4-0 5요소를 따른다. 위배 시 §11 4블록 자체 검증 + Codex Gate C advisory 발동:

- (i) **4명 동시 spawn 시작점**: /kickoff [2]에서 service-planner 동시 spawn. 본 Skill은 spawn 직후부터 호출 가능
- (ii) **부분 broadcast 연속 흐름**: PRD 작성 중 부분 확정 사건마다 즉시 발행 (묶음 broadcast 금지)
- (iii) **양방향 reply**: 후행 영역(TR/UX/P)에서 reply 받으면 자가점검 재발동 + 보강 + broadcast 재발행
- (iv) **자가점검 = 완성 검증**: PRD 완성 시점 1회. 후행 영역(TR/UX/P) 진입 트리거 *아님*. 후행이 *완성 산출물 사용 시점*에만 게이트 (CLAUDE.md §6-2)
- (v) **모든 영역 병렬·유기**: reply 처리 중에도 자기 영역 다른 작업 진행 계속

## 호출 절차

### 1. STATE.md + `_broadcast.log` first read (CLAUDE.md §6)

- 고객사·PM·현재 단계·시작/종료일 확인
- `_broadcast.log`에서 다른 영역의 reply 수신 여부 확인
- 이미 `01-prd.md` 존재 시 덮어쓰기 금지 — 팀장에게 보고 (CLAUDE.md §9)

### 2. 입력 요구사항 수집 + §0 PM 원본 *그대로 삽입* (PI-009 — 의도 SSoT)

- **§0 PM 원본 = 변환·삭제 금지** (영역 침범, 자동 실패 조건 A-1)
- 부족한 입력은 `AskUserQuestion`으로 질의 → 응답을 *원문 그대로* §0-4에 삽입
- §0 4 sub-section 매핑:
  - §0-1: PM 발화 원문
  - §0-2: 사업계획서·RFP·제안서 원문
  - §0-3: 인터뷰·이메일·메모 원문
  - §0-4: AskUserQuestion 응답 원문
- **수집 항목 (PM 원본에서 추출)**:
  - 고객사명·프로젝트명 (필수)
  - WHY (비즈니스 배경·문제·기회)
  - 1차 사용자 (1명 명확)
  - 도메인 분류 (대분류·중분류·소분류·업무영역명) — REQ ID `REQ-{도메인}-NNN-NN` 4 segment 정의
  - 요구사항 카탈로그 항목 (16 필드별 입력)
  - 경계 사례(SSO·결제·2FA·이미지 업로드 등) 명시 사항 — *PRD 명시 의무* (PI-011, 자동 실패 조건 A-4)
  - 특정 로직(결제 흐름·도메인 로직) — PM `AskUserQuestion` 추가 질의 (PI-012)
  - 표준 패턴 자율 결정 사항(로그인·회원가입 등) — §C 1줄 기록 대상 (PI-013)
  - 오픈 이슈 (담당자·기한 필수)

### 3. template.md 로드 → 6 섹션 채우기 (부분 broadcast 연속 흐름)

§0 PM 원본 → §A 비전 → §B 요구사항 카탈로그 → §C 표준 패턴 → §D 오픈 이슈 → §E 자가 점검 순서. 단 *부분 확정 사건마다 즉시 broadcast 발행* (§4-0 (ii) — 묶음 금지):

#### 부분 broadcast 트리거 (PRD 작성 중 즉시 발행)

| 트리거 사건 | broadcast 대상 |
|-------------|----------------|
| §0 PM 원본 1줄 확정 | 전체 (TR/UX/P) |
| §A WHY 확정 | 전체 |
| §A 1차 사용자 확정 | 전체 |
| §B 요구사항 1건 16 필드 일부 채움 (4~6 필드+) | 전체 |
| §B 요구사항 1건 16 필드 모두 완성 (REQ-{도메인}-NNN-NN 확정) | 전체 |
| §C 표준 패턴 자율 결정 | 전체 (참고 정보) |
| §D 오픈 이슈 추가 | 전체 |

발행 방식: `SendMessage`(broadcast) 또는 `_broadcast.log` 8필드 기록 (type=`broadcast`, owner=`REQ`, target=`PRD §N`)

#### 작성 시 본질 영역

- **§A 비전**: WHY + 1차 사용자만. **KPI(성공 지표) 작성 금지** (PI-008)
- **§B 요구사항 카탈로그**:
  - 대분류별 그룹화 §B-1·§B-2·... (PI-006)
  - 각 요구사항 = 16 필드 표 (필수 13 + NA 허용 3 — 소분류·제약사항 및 전제조건·기타사항)
  - REQ ID = `REQ-{도메인 2~4글자}-{NNN}-{NN}` 4 segment 정합 (PI-004, 정규식 `^REQ-[A-Z]{2,4}-\d{3}-\d{2}$`)
  - *출처* 필드 = §0 PM 원본 인용 형식 (예: "§0-3 PM 메모 4단락")
  - **경계 사례** (SSO·결제·2FA·이미지 업로드 등) = §B 16 필드로 명시 의무 (PI-011, 자동 실패 조건 A-4)
- **§C 표준 패턴**: 자율 결정 발생 시 1줄 기록 (`(YYYY-MM-DD) 영역: default 결정`). ID 부여 없음 (PI-013). NA 허용
- **§D 오픈 이슈**: 모든 행 담당자·기한 필수 (CLAUDE.md §7)

### 4. 특정 로직 발견 시 PM 추가 질의 (PI-012)

PRD 작성 중 다음 영역 발견 시 자율 결정 금지:
- 결제 흐름 (결제 수단·환불 정책·정기 결제)
- 도메인 로직 (랭킹 산정·매칭 알고리즘·점수 계산 등 프로젝트 본질 로직)
- 비표준 비즈니스 로직

처리: `AskUserQuestion` 즉시 발행 또는 controller 경유 PM 확인 → PM 결정 → §B 명시 + Decision Log 기록.

### 5. 다른 영역 reply 수신 시 처리 (§4-0 (iii))

후행 영역(TR/UX/P)이 PRD 모순·누락 발견하여 `SendMessage`(reply) 발행한 경우:
- 자가점검 재발동 → §B 보강 → broadcast 재발행
- 자기 영역 다른 작업은 진행 계속 (§4-0 (v))

### 6. checklist.md 로드 → 자가 점검 (§4-0 (iv) 완성 검증 한정)

산출물 하단 §E 섹션에 결과 기록:

#### §A 자동 실패 조건 (4건 — 1건 위배 시 즉시 재작성)

- A-1: §0 PM 원본 보존 (변환·삭제 0건)
- A-2: §B 16 필드 필수 13 채움
- A-3: §B REQ ID 4 segment 정규식 정합
- A-4: §B 경계 사례 PRD 명시 (자율 결정 우회 0건)

#### §A 통과율 7항목 (6/7 이상 통과, 5/7 이하 재작성)

- B-1~B-7: 비전 / 출처 / 분류 / 유형 / 담당자 / §C 형식 / §D 오픈 이슈

#### §B M11 v1 cross-ref (8필드 형식, M9 §10-2-2)

- F-1~F-8 ID·헤더·NA / M-a·M-d 매핑 / H-1·H-2·H-5 휴리스틱 / U-1~U-5 범용

**통과 기준**: §A 자동 실패 0 위배 + 통과율 ≥ 6/7 + §B error 0 → 후행 영역 *완성 산출물 사용 게이트* 통과.

⚠️ **자가점검 통과는 *완성 신호*이지 후행 영역 진입 트리거 아님** — 후행은 부분 broadcast마다 즉시 진행 (§4-0 (iv)).
