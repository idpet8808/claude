# 기술 검토서 자가 점검 체크리스트 (5항목)

기술검토자가 검토서 작성 직후 1차 게이트, 팀장 Claude가 UX기획자 호출 전 2차 게이트로 사용.
통과 기준: **4/5 이상 (80%)** — 단, CLAUDE.md §5 기준인 85% 엄격 적용 시 **5/5 필수**.

---

## 1. Must 기능 전수 평가가 되어 있는가?
- [ ] 검토서 `2. Must 기능 전수 평가` 표의 행 수가 PRD `4. Must` 섹션 기능 수와 **정확히 일치**
- **실패 예**: Must 5개 중 3개만 평가
- **이유**: 누락된 Must는 개발 착수 후 폭탄이 된다

## 2. 리스크별 완화책이 명시되어 있는가?
- [ ] `4. 리스크 분석` 표의 모든 리스크에 **완화책** + **담당자** 컬럼이 채워짐
- **실패 예**: "보안 리스크 있음" (대응 없음)
- **통과 예**: "SQL Injection → 파라미터 바인딩 강제 + 코드리뷰 게이트, 담당: 백엔드 리드"

## 3. 공수 3시나리오가 수치화되어 있는가?
- [ ] `6. 공수 산정` 표에 **낙관/현실/보수 세 값이 모두** 숫자(주 단위)로 기입
- **실패 예**: 공수 "3개월 내외" (단일 추정)
- **이유**: 3시나리오 없이는 일정 리스크를 PM이 판단할 수 없음

## 4. 외부 의존성이 확인되어 있는가?
- [ ] `5. 외부 의존성` 표의 모든 행에 **버전** + **라이선스** + **확인 여부(Y/N)**
- **이유**: 라이선스 위반·버전 호환성 문제는 검토 단계에서 발견하지 않으면 배포 직전에 폭발

## 5. 모든 판단에 PRD 섹션 인용이 있는가?
- [ ] Must 기능 평가의 `참조` 컬럼이 `01-prd.md §N` 형식으로 채워짐
- **이유**: PRD 없이 독자 상상한 평가는 CLAUDE.md §5 영역 침범. 인용은 추적성의 증거

---

## 점수 해석
- **5/5**: 즉시 UX기획자 호출 가능
- **4/5**: 통과하되, 미달 항목을 오픈 이슈로 이동 후 호출
- **3/5 이하**: 재작성 필수
- **3회 연속 3/5 이하**: PRD 자체에 문제 → 서비스기획자에게 반려
